# Claim Audit — how to test a technical claim

Use this when a passage makes more than a couple of claims, or when a claim is load-bearing for plot.

## 1. Find the claims, including the hidden ones

Explicit claims are easy ("the enzyme breaks down in forty minutes"). The dangerous ones are implied:

- **Agency verbs.** "The system decided / wanted / realized / knew." Each is a claim about mechanism. Ask what actually happened: a threshold was crossed, a rule fired, a pattern matched, a person approved.
- **Certainty words.** "Proved," "confirmed," "impossible," "guaranteed." Most real evidence is partial.
- **Time and scale.** "Overnight," "instantly," "every hospital," "the whole network." Check the order of magnitude.
- **Cost-free fixes.** A solution with no price, delay, staffing, or failure mode.
- **Borrowed authority.** Named standards, laws, agencies, papers, or products. These must be real and described accurately, or clearly fictional.

## 2. Classify

| Type | Test | What "correct" means |
|------|------|----------------------|
| Real-world fact | Would a reference source settle it? | True as of the research cutoff; cited when corrected |
| Book invention | Is it a fictional system, org, law, or product? | Internally consistent; built from real mechanisms; logged in the canon ledger |
| Speculative extrapolation | Does it go past current capability on purpose? | Extends a named real mechanism; the book frames it as premise, not present fact |

## 3. Evidence discipline

Keep these separate on the page and in the edit notes:

- **Observed** — a record, a measurement, a log line, a test result.
- **Inferred** — a supported conclusion from observations. Say what supports it.
- **Unknown** — what the characters can't yet establish. Leaving it unknown is often better drama.

Common over-claims to soften:

- An explanation of one output presented as the system's private reasoning.
- A single matching case presented as proof of the whole pattern.
- A signature, hash, certificate, or audit presented as proof the underlying data is true (it usually proves origin or integrity, not accuracy).
- A study, benchmark, or percentage the book invented presented as an external finding.
- Access or ownership presented as proof someone took a specific action.

## 4. Practitioner wince test

Ask: would someone who does this job for a living stop reading here? Typical winces:

- The expert explains basics to another expert who would already know.
- Jargon used as decoration rather than because that's how the work sounds.
- A failure mode chosen for drama when the real system would fail somewhere else (the real seam usually makes the better scene).
- A procedure that skips the steps everyone in the field complains about.

## 5. Handle test

For each concept a lay reader needs, find a handle: something they already own that maps onto the mechanism truthfully. Good handles are concrete (a locked room you can work inside; a filing cabinet that files by meaning). Test the handle both ways: does it explain the concept, and does it avoid implying something false?

## 6. Right-sizing the fix

- Change the fewest words that make the claim true.
- If the true version is less dramatic, look for the drama inside the real limit before softening the scene.
- If the fix changes a plot fact, flag it for `continuity-editor` and for the author's approval.
